# 《医学人工智能系统设计》课程项目设计说明



## 0. Abstract --to be done

这份设计说明对应的不是一个假想方案，而是我们已经完成并跑通的项目成果。不过，如果只把它描述成“一个能问症状、出摘要、推荐科室的 Web Demo”，其实低估了我们真正想做的事情。更准确的定义应该是：**“主动式多智能体医疗预审系统（Proactive Multi-Agent Medical Triage System）”的第一阶段雏形。**

在这个定义下，当前版本并不是终局，而是一个核心骨架。它首先验证的是最关键、也最难跳过的一段核心链路：**自然语言输入能否稳定沉淀为结构化病历摘要，并进一步转化为分诊建议、风险提醒和接诊前资料。** 这一步之所以重要，是因为未来不管系统演化成多智能体协同网络、接入时序生理数据，还是变成能直接操作临床软件环境的实体 Agent，都必须先拥有这条“从混乱输入到结构化医疗表示”的基础能力。

因此，我们更愿意把当前系统理解为一个“智能预审内核”的起点。它已经不只是一个问诊对话框，而是在门诊前置流程中承担起了信息整理、风险初筛、流程衔接和结果组织的角色；在更长远的设想里，它会进化为一个能够主动调度多类智能体、接管复杂临床工程任务、并在医生接诊前完成大量准备工作的医疗 AI 基础设施。

## 1. Introduction

### **1.1 Background.** 

近年来，随着大语言模型与自然语言处理技术的突破，人工智能在医疗领域的应用正从单一的感知任务（如医学影像病灶分类）向复杂的认知与交互任务深层演进。在整个医疗服务体系中，门诊初筛与预问诊 作为连接患者与医疗资源的第一道关口，其效率与准确性直接决定了后续诊疗的质量。

然而，当前的门诊接诊流程正面临着显著的信息断层挑战。在真实的就诊场景中，患者对病情的描述往往是高度口语化、非结构化且信息高度离散的，例如“发烧咳嗽好几天了”。而在问诊台的另一端，医生在极其有限的单次接诊时间内，迫切需要的是符合临床思维的高度结构化病历信息（如主诉、现病史、既往史及伴随症状）。这种输入与需求之间的错位，导致医生不得不耗费大量宝贵的面诊时间，用于执行重复的信息采集与重组工作。

尽管目前已有一些信息化的预问诊尝试，但现有的解决方案多存在明显局限。传统的系统大多依赖僵化的静态表单填报，极大地损害了患者体验；而初级的对话机器人往往仅具备被动式的一问一答功能，缺乏深度的医学逻辑推理能力。它们不仅无法将患者的自然语言实时沉淀为标准的医疗中间表示，更难以在繁杂的对话中敏锐捕捉到潜在的危急重症风险，比如将“胸痛伴呼吸困难”识别为需要立即干预的红旗征象。这种被动性与割裂感，导致现有系统很难真正融入并优化临床工作流。

鉴于此，打破这一瓶颈的关键，在于构建一个具备主动认知能力的新型预审架构。医疗 AI 系统的发展方向，不应仅仅是等待输入指令的问诊对话框，而应演进为能够在接诊前主动收集、结构化整合信息并进行风险初筛的主动预审模块。这也是本系统设计的核心出发点与立足点。

### **1.2 Problem. ** 

为了缓解门诊资源错配并提升接诊效率，我们设计并实现了一个医疗预审系统原型。在这一场景下，系统的核心输入是患者的自由文本对话以及部分多模态资料，比如患处图像。基于这些非结构化输入，我们的首要任务是构建一条稳定且自动化的数据处理链路，将口语化的病史精准映射为高度结构化的医疗特征表示（如主诉、持续时间、伴随症状等）。

此外，真实临床实践中危急重症往往隐藏在极其普遍的症状组合中（例如胸痛伴发呼吸困难），这一事实启发我们进一步探索风险仲裁机制。这种机制是门诊分流安全性的关键因素。

为了解决上述问题，本系统旨在提供一种自动化预审方案。一种更为激进的替代方案是构建一个端到端（End-to-End）的全自动医疗智能体，也就是直接越过分诊台，将诊断结果写入医院信息系统并下达处方。然而，正如谢医生在课上分享的角膜病案例一样，即使ai的识别成功率比人类专家更高，医疗领域的极高容错成本、大模型的固有幻觉问题，以及复杂系统间的权限壁垒，导致在完全解决 AI 决策的可解释性之前，盲目追求端到端的全自动化将带来极大的临床风险。

因此，我们在本阶段的工作中缩小了研究的范围，专注于解决预审流程中最基础、也是最安全的任务：实现患者口头描述症状，到医生端生成结构化病例的过程。在解决这个问题之前，很难直接探讨更复杂的实体 Agent 环境接管诊疗。这也是本系统作为第一阶段雏形的核心定位。

### 1.3 Solution

为了应对上述挑战，在本项目中，我们提出并实现了一个新颖的主动式医疗预审系统原型。

为了处理**第一个挑战（高度口语化与非结构化的输入）**，我们旨在构建一个能将口语化的输入转化为结构化的输出的映射。为此，本系统采用了一种**正则匹配与大语言模型相混合的架构**。具体而言，大语言模型作为核心的认知引擎，负责理解复杂的上下文并执行结构化 JSON 的生成；同时，系统在本地前置了基于正则匹配与医学词典的启发式规则链路，用于对体温、年龄、持续时间等确定性生命体征进行强制校验与提取。这种双线设计确保了的更高的稳定性。

针对**第二个挑战（初始输入的信息稀疏性）**，本系统采用了一种**主动式槽位填充机制**。与传统的被动式问答机器人不同，系统会在每一轮对话后实时评估当前结构化摘要的完整度。当发现关键分诊信息（如疼痛的具体放射位置、确切最高体温）缺失时，系统会通过动态组装的 Prompt 驱动大模型生成高度针对性的追问，从而在多轮自然交互中逐步引导患者补全病史。

最后，为了使系统在面对极其普遍的症状噪声时具备**更高的安全鲁棒性（应对第三个挑战）**，我们提出了一种风险评估机制。受到临床医生真实诊断过程的启发——医生通常会综合微观症状与宏观危急信号来做出判断——我们提出让系统在三个层级上同步处理信息：**实体层（微观层，Micro-level，如提取“胸痛”、“咳嗽”词汇）**、**专科层（中观层，Meso-level，如计算呼吸科或心内科的匹配权重）**以及红旗层（宏观层，Macro-level，如识别“胸痛伴呼吸困难”的高危组合）。具体而言，系统设定了严格的自上而下的阻断逻辑：一旦在宏观层（红旗层）匹配到高危特征网络，该层级的安全指令将直接覆盖并削弱中微观层级的普通专科推荐逻辑，强制将就诊优先级提升为“紧急（Emergency）”。直观地说，系统在较高层级聚合安全底线信息，进而向下干预输出，极大地降低了因大模型微观幻觉而导致重症漏诊的可能性。

## 2. 系统概览与交互呈现

接下来，在进入底层的代码架构前，让我们先直观地展示一下这个系统跑起来到底是什么样子。作为一个完整的课程原型，我们花了不少心思在用户交互（UI/UX），试图让它摆脱单纯的命令行脚或简陋聊天框。

### 2.1 核心功能与界面呈现

最开始构思界面时，我们其实也想过直接套用类似 ChatGPT 那种单栏的对话窗口。但在真实的医疗场景里，如果医生和患者只是面对一个纯聊天的瀑布流，医生依然需要费力地去上下翻找体温、症状时长这些关键信息。因此，为了真正解决“信息提炼”的问题，我们决定采用**左右双栏**的布局设计：

- **左侧（自然交互区）：** 这里的视觉逻辑非常像大家最熟悉的微信聊天。它最大的作用是**降低门槛**，患者不需要对着一张复杂的医疗表格发呆，直接用大白话输入“我这两天嗓子疼，还有点发烧”即可。在这个区域的底部，我们不仅保留了文本输入，还加上了多模态的入口（允许患者上传皮损照片或化验单），让交互方式尽可能贴近现实。
- **右侧（结构化沉淀区）：** 这是我们系统最核心的“门面”。当左侧的聊天还在进行时，右侧的面板会像一个不知疲倦的医生助理，实时把聊天的内容“翻译”并填入一张结构化的卡片中。主诉、持续时间、既往史、甚至是专门给医生看的极简摘要，都会在这里整齐排列。
- 除此之外，在界面的顶部，我们设计了一个下拉菜单，允许在不同的模型通道（如 Mock 规则模式、豆包模型、DeepSeek 模型）之间一键切换。Mock模式没有调用大模型，而是使用硬编码的方式对患者的输入进行匹配和输出，速度快但是范围不广；豆包能识别图像资料，但是速度慢；DeepSeek不能识别图像，但是速度快。

![image-20260330230341057](/Users/syw/Desktop/pre-consult-ai/docs/image-20260330230341057.png)

除了面向患者的问诊界面，为了真正打通医疗工作流，我们还独立开发了**医生端·实时结构化摘要监控台**。在这个独立页面中，我们完全去除了冗余的聊天对话框，取而代之的是纯粹的医学数据看板。系统通过前后端实时通信机制，将患者在候诊区聊天的内容，毫秒级地转化为医生桌面上的结构化卡片（包括接诊前一句话摘要、主诉、风险红旗征象等）

### 2.2 患者端交互闭环

为了更清晰地感受我们的系统的雏形，我们不妨模拟一位真实患者（比如因为发热、咳嗽伴随胸痛来就诊），来走一遍完整的体验流程。**第一步：初始输入与初步提炼**

患者一上来可能表达得很零散（例如只发了一句“有点咳嗽，还有点胸口疼”）。当这条消息发出去后，系统并不会像死板的客服机器人那样立刻甩出一个长篇大论的医疗免责声明，而是会一边在右侧面板悄悄记录下“咳嗽”和“胸痛”，一边进入第二步的主动交互。

**第二步：AI 主动式槽位填充**

这是我们觉得做得很“智能”的一个点。系统后台发现右侧面板里“具体体温”和“疼痛性质”是空缺的，于是它会在右侧的【仍待补充信息】卡片里列出这些盲点，并同时在左侧聊天框里主动向患者发起追问：“请问您有测量具体体温吗？胸口是闷痛还是刺痛呢？”这种带有规划性的主动引导，是我们迈向医疗 Agent的第一步尝试。

**第六步：医生端实时同步**

医生不需要去翻看患者刚才那几十条口语化的聊天记录。系统已经在最醒目的位置生成了极简的**“接诊前摘要”**（例如：“患者主诉咳嗽、胸痛，伴有呼吸困难”），并用醒目的红色高亮了“紧急”的就诊优先级。这种前置的数据处理，让医生在患者推门进来的前 3 秒钟，就已经在脑海中建立起了初步的诊断防线。同时，页面右上角保留的“复制摘要”和“下载 JSON”功能，也为未来系统直接将数据无缝对接写入医院真实的 HIS（医院信息系统）预留了标准化接口。

### 3. 系统架构与数据流

看完了系统跑起来的直观效果，我们把它的外壳拆开，看看支撑这些交互的底层部分。

#### 3.1 总体分层架构

整个系统由上至下划分为四个极其清晰的层级。这里我们没有引入过于笨重的微服务框架，而是主打轻量与敏捷：

![系统总体架构](/Users/syw/Desktop/pre-consult-ai/docs/system-architecture.svg)

- **第一层：展示层 (Presentation Layer)。** 对应前端的 HTML 和 JS 代码。除了实现前面提到的“左右双栏联动”，它还负责管理局部的状态（比如聊天记录的数组维护、多模态图片的 Base64 实时转换）。
- **第二层：应用层 (Application Layer)。** 基于轻量级的 Flask 框架搭建。作为承上启下的枢纽，它暴露了 `/api/chat`（核心对话）、`/api/appointments`（模拟挂号）等 Restful 接口，负责请求的校验、拦截和响应分发。
- **第三层：模型与逻辑层 (Model & Logic Layer)。** **这是整个系统的心脏。** 我们在这里设计了“规则解析”与“大模型推理（豆包/DeepSeek）”并行的双轨制链路。它不仅要负责和外部 AI 接口打交道，还要运行本地的红旗征象仲裁算法。
- **第四层：数据与配置层 (Data & Config Layer)。** 为了保证原型的轻量化，当前版本没有挂载重型数据库。排班信息、医学词典（症状正则匹配库）和环境变量全都在本地内存和配置文件中维护，确保系统能够做到真正的“开箱即用”。

#### 3.2 动态问诊数据流

静态的架构图可能不足以说明系统是怎么“转”起来的。我们以患者在界面上发送一句**“我发烧咳嗽三天了，喉咙也有点痛”**为例，追踪一下这条数据在系统内部跑完一个闭环的全过程：

![问诊数据流](/Users/syw/Desktop/pre-consult-ai/docs/interaction-flow.svg)

1. **打包发送：** 患者点击发送，前端立刻将这句话与历史聊天记录拼接成 `messages` 数组，如果附带了图片则转换为 Base64，通过 `/api/chat` 接口发起异步请求。
2. **校验与路由：** Flask 后端接收到请求后，首先拦截并校验消息格式。确认无误后，根据前端选定的通道（Mock/豆包/DeepSeek）进行分发。
3. **双轨解析引擎处理（核心动作）：**
   - *规则提取：* 本地正则引擎瞬间扫过文本，抽取出“发热”、“咳嗽”等实体，并提取出“三天”这个时间特征。
   - *模型推理：* 系统的 Prompt 引擎将聊天记录打包装配，请求大模型进行深度的语义理解，并强制要求大模型吐出标准格式的 JSON 数据。
4. **特征归一化与红旗仲裁：** 后端拿到模型返回的 JSON 后，并不会直接信任。系统会执行统一的字段校验（Normalization），补齐缺失字段，最关键的是**触发红旗征象检测逻辑**（比如后续发现“胸痛”，立马强行篡改模型输出的优先级，拉高为“紧急”）。
5. **前端响应与 UI 刷新：** 经过层层把关的纯净 JSON 数据被送回前端。前端根据这些结构化字段，瞬间刷新右侧的所有病历卡片；如果检测到“紧急”标志，则立刻在界面弹出红色的预警框。

### 4. 演进蓝图：迈向主动式多智能体生态 

如果仅仅将当前的系统视为一个具备结构化能力的问诊对话框，无疑是对其底层潜力的低估。我们在本阶段构建的双轨制抽取、主动槽位填充与风险仲裁机制，本质上是为了提炼出一种标准化的医疗中间表示（Medical Representation）。

一旦这种标准化的高质量数据流得以确立，系统便具备了向更高维度的智能形态演进的基础。在我们的中长期演进蓝图中，本系统将从一个单体预审工具，蜕变为一个多智能体网络。这种多智能体博弈能极大减少单一模型的“偏见盲区”，不仅能给出科室推荐，还能在摘要中附带一句：“心内科排查优先度 80%（需排除急性冠脉综合征），消化内科排查优先度 20%”。

#### 4.1 从单一文本预审，到“专科 Agent”的协同会诊 

当前的大模型虽然具备通用的医学常识，但在处理复杂的跨系统并发症时，往往缺乏专科级别的深度推理能力。未来的系统后台将演变为一个高度解耦的**多智能体协同系统**。

![多智能体](/Users/syw/Desktop/pre-consult-ai/docs/多智能体.png)

- **专科化分工与并行处理：** 系统不再由单一的 LLM 统揽全局，而是孵化出多个具备独立人设和特定知识库的专科 Agent（如“心血管 Agent”、“呼吸科 Agent”、“消化科 Agent”等）。当获取到患者的结构化病历（如“胸痛、咳嗽、伴有反酸”）时，分发路由会将信息同时广播给所有相关的专科 Agent。

- **模拟多学科会诊的仲裁机制：** 各专科 Agent 将基于自身的视角给出诊断假说。例如，心血管 Agent 会重点排查心绞痛，消化科 Agent 会怀疑胃食管反流，而呼吸科 Agent 会考虑胸膜炎。此时，系统中央的**“风险仲裁 Agent”**将介入，综合各方置信度，甚至主动发起跨 Agent 的辩论，最终收敛出一个安全性最高、逻辑最严密的分诊与排查建议。

  这种多智能体博弈能极大减少单一模型的偏见或幻觉，不仅能给出科室推荐，还能在摘要中附带一句：“心内科排查优先度 80%（需排除急性冠脉综合征），消化内科排查优先度 20%”。

  

#### 4.2 从静态离散问诊，到连续时序生理数据的联合建模

![timeseries](/Users/syw/Desktop/pre-consult-ai/docs/时序.png)

真实的疾病发展从来不是一个个孤立的静态文本切片，而是一个随着时间推移、在身体不同空间部位蔓延的动态过程。未来的预审系统必须打破静态文本的局限，将目光投向连续的生理时间序列。

- **接入动态时序信号：** 现代患者往往佩戴有智能腕表或连续血糖监测仪等可穿戴设备。系统未来可开放授权接口，在患者输入“我最近老是头晕心慌”的同时，后台同步调取其过去 72 小时的连续心率、心率变异性（HRV）、血氧饱和度甚至深度睡眠分期等高频时间序列数据。

- **时空数据建模与前瞻性预测：** 传统的自然语言处理只能做到“事后总结”，而引入时间序列预测后，系统将具备前瞻性的预警能力。AI 可以敏锐地捕捉到时序波形中那些难以被患者察觉的微小异常波动。例如，不仅能记录患者“右下腹痛”，还能结合其过去 12 小时的疼痛转移轨迹（从胃部逐渐转移至右下腹），通过时空动态图特征，精准预测阑尾炎的爆发节点。

  

#### 4.3 迈向“实体 Agent”的闭环接管与环境交互 (Embodied Agent for Clinical Workflows)

![Gemini_Generated_Image_2oinsl2oinsl2oin](/Users/syw/Desktop/pre-consult-ai/docs/Gemini_Generated_Image_2oinsl2oinsl2oin.png)

预审的终极形态，是让 AI 拥有一双能够操作现实医疗软件的“手”。未来的系统将从“只能提供建议的咨询师”，升级为“能够主动接管繁杂事务的实体智能体（Embodied Agent）”。

- **跨系统的数据调取与整合：** 在确保隐私合规的前提下，系统将获得对接医院核心系统（如 HIS、LIS、PACS）的只读权限。当确认患者身份后，数据检索 Agent 会在医生接诊前，自动爬取该患者过去三年的历史门诊记录、历次化验单数据以及用药清单。
- **沙盒环境内的主动数据分析：** 系统将不仅限于文本输出，更能自主编写代码执行复杂的数据分析任务。例如，针对一位慢性肾病患者，数据处理 Agent 可以自动在安全的沙盒环境（Sandbox）中生成一段 Python 脚本，将患者过去十次化验单中的“血肌酐”和“尿素氮”指标提取出来，绘制成直观的趋势折线图。
- **具体场景示例：** 当患者推开诊室大门时，医生看到的不再是一堆需要人工翻阅的零散单据，而是一份由实体 Agent 自动生成并排版完毕的综合数字面板。面板上既有患者几分钟前刚口述的结构化症状，也有多智能体给出的高危预警，甚至还附带了历史核心指标的时序趋势分析图。这才是一个真正融入医疗工作流、释放医生生产力的究极 AI 基础设施。
